# Перевірка комплекту документації

Цей посібник призначений для перевірки артефактів після їх майбутнього створення. У межах поточного планувального workflow діаграми та XLSX не генеруються, тому перевірки файлів поки що не пройдуть.

## Передумови

- Робоча копія репозиторію та командний рядок.
- Після реалізації мають існувати `docs/usecase.puml`, `docs/class.mmd`, `docs/sequence.mmd`, `docs/state.mmd`, `docs/crc.xlsx`.
- Для повної перевірки — доступні локально валідатори PlantUML і Mermaid та засіб читання XLSX. Їхні версії/спосіб встановлення не задані специфікацією; не додавайте ці засоби до runtime-залежностей застосунку.

## Сценарій 1: наявність обов'язкових файлів

З кореня репозиторію:

```sh
for f in docs/usecase.puml docs/class.mmd docs/sequence.mmd docs/state.mmd docs/crc.xlsx; do
  test -s "$f" || { echo "Відсутній або порожній файл: $f"; exit 1; }
done
echo "Усі п'ять артефактів наявні"
```

Очікувано: команда завершується з кодом `0` і виводить повідомлення про наявність усіх п'яти файлів.

## Сценарій 2: синтаксична перевірка діаграм

Якщо локально встановлено командні валідатори:

```sh
plantuml -checkonly docs/usecase.puml
mmdc -i docs/class.mmd -o /tmp/property-class.svg
mmdc -i docs/sequence.mmd -o /tmp/property-sequence.svg
mmdc -i docs/state.mmd -o /tmp/property-state.svg
```

Очікувано: кожна команда завершується успішно; Mermaid-перевірка створює рендери у `/tmp`, не змінюючи артефакти репозиторію. Якщо конкретна версія CLI використовує інші параметри, застосувати еквівалентний режим перевірки її локальної документації та зафіксувати команду.

## Сценарій 3: змістова звірка

Перевірити діаграми та специфікацію за [моделлю даних](data-model.md) і вимогами `FR-001`—`FR-021`:

1. Use-case має трьох акторів, усі потрібні операції та участь кожного актора.
2. Class diagram містить не менш як три класи, інтерфейс, абстрактний клас, конструктор і атрибут/метод у кожного класу, `final`-метод, наслідування, реалізацію, залежність та агрегацію/композицію.
3. Кожне класове посилання в атрибуті/методі має відповідний зв'язок; sequence participants мають типи з class diagram.
4. Сценарії страхування та випадку узгоджуються зі станами заявки, поліса, збитку й виплати; присутні початковий і кінцевий стани, нульова оцінка та відмова для завершеного поліса.
5. Текстові описи українські; програмні назви англійські; реальні зовнішні операції та БД відсутні.

Очікувано: немає суперечностей між акторами, повідомленнями, сутностями, зв'язками, станами й позначенням симуляції.

## Сценарій 4: перевірка CRC-книги

Відкрити `docs/crc.xlsx` у сумісному табличному переглядачі або перевірити локальним XLSX-читачем:

- кожен аркуш/картка відповідає класу діаграми класів;
- заголовок таблиці дорівнює назві класу;
- таблиця має рівно дві колонки в порядку «обов'язки класу», «з ким співпрацює»;
- на картці не більше чотирьох коротких відповідальностей у формі «дієслово + іменник»;
- співпраці записані назвами наявних класів.

Очікувано: 100% класів мають картку, зайвих/відсутніх класів і третьої колонки немає.

## Критерій завершення

Приймання успішне, якщо всі файли наявні, синтаксис діаграм валідний, зміст покриває `SC-001`—`SC-007`, а CRC-картки повністю відповідають class diagram. Цей плановий крок не генерує самі п'ять цільових файлів.
