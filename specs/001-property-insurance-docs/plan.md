# План реалізації: документація страхування майна

**Гілка**: `001-property-insurance-docs` | **Дата**: 2026-11-20 | **Специфікація**: [spec.md](spec.md)

**Вхідні вимоги**: `specs/001-property-insurance-docs/spec.md`

## Підсумок

Підготувати взаємоузгоджений комплект із чотирьох текстових UML/Mermaid-діаграм та книги CRC-карток XLSX для навчальної предметної області «Страхування майна». План передбачає моделювання ролей клієнта, страхового агента й експерта-оцінювача; окремих життєвих циклів заявки, поліса та страхової заяви; а також перевірку узгодженості типів, зв'язків, станів і CRC-карток. Зовнішні операції відображаються лише як консольна симуляція. Самі діаграми, таблиця та код застосунку в межах цього планувального workflow не створюються.

## Технічний контекст

**Мова/версія**: Java для майбутнього навчального застосунку; версію Java специфікація не задає, тому для діаграм версію не фіксуємо.

**Основні залежності**: PlantUML для `docs/usecase.puml`; Mermaid для `docs/class.mmd`, `docs/sequence.mmd`, `docs/state.mmd`; формат XLSX для `docs/crc.xlsx`. Сторонні runtime-бібліотеки не додаються.

**Зберігання**: файли документації у `docs/`; база даних не використовується.

**Тестування**: перевірка наявності й форматів артефактів, розбір PlantUML/Mermaid на синтаксичні помилки, огляд зв'язків і станів, перевірка структури XLSX та звірка всіх CRC-карток із класами. Інструменти валідації можуть запускатися з командного рядка; їх встановлення не є runtime-залежністю застосунку.

**Цільова платформа**: самодостатній навчальний Java CLI, що запускається з командного рядка; поточний обсяг цієї задачі — платформонезалежні файли документації.

**Тип проєкту**: документаційний комплект до навчальної CLI-системи.

**Цілі продуктивності**: не застосовуються.

**Обмеження**: пояснення українською, назви програмних елементів англійською; зовнішні інтеграції та БД відсутні; DI — лише через конструктори/setter-и; моделювання має відповідати SOLID і конституції.

**Масштаб/обсяг**: чотири діаграми у визначених специфікацією шляхах та одна XLSX-книга з CRC-карткою для кожного класу діаграми класів. За межами — реалізація Java-застосунку й самих артефактів на цьому етапі планування.

## Перевірка конституції

*Контрольні ворота до дослідження та після проєктування.*

| Принцип / обмеження | Перевірка плану | Результат |
|---|---|---|
| I. Мінімальна складність | Моделюються лише ролі й сутності, необхідні для вимог; інтеграційні сервіси та БД не додаються. | Пройдено |
| II. Єдина відповідальність | Кандидатні класи розділяють клієнта, заявку, оцінку, поліс, страховий випадок і виплату. | Пройдено |
| III. Симуляція зовнішніх операцій | Операція виплати/зовнішнього повідомлення у сценарії є лише консольним повідомленням через абстракцію симулятора. | Пройдено |
| IV. CLI та відсутність сервісів/БД | Заплановані лише файли документації; інтеграції та постійне сховище виключені. | Пройдено |
| V. Явне впровадження залежностей | Залежність агента від симулятора показується як абстракція, що передається конструктором або setter-ом. | Пройдено |
| VI. Мова коду й пояснень | Пояснювальні тексти — українською; назви класів, методів і атрибутів — англійською. | Пройдено |
| VII. Текстові UML-діаграми | Чотири діаграми зберігаються у текстових PlantUML/Mermaid-файлах у `docs/`. | Пройдено |
| VIII. Україномовна специфікація | Цей план і дизайн-артефакти написані українською. | Пройдено |

**Рішення щодо воріт**: невирішених суперечностей із конституцією не виявлено; винятки не потрібні. Після Phase 1 усі принципи повторно перевірено за тим самим переліком — порушень немає.

## Структура проєкту

### Документація цієї задачі

```text
specs/001-property-insurance-docs/
├── plan.md
├── research.md
├── data-model.md
├── quickstart.md
└── checklists/
    └── requirements.md
```

`contracts/` не створюється: задача визначає локальні документи, а не зовнішній API, CLI-контракт чи протокол інтеграції. Контрактами приймання є вимоги `FR-001`—`FR-021` та критерії `SC-001`—`SC-007` у специфікації.

### Цільові артефакти функції (пізніша реалізація)

```text
docs/
├── usecase.puml
├── class.mmd
├── sequence.mmd
├── state.mmd
└── crc.xlsx
```

**Рішення щодо структури**: у поточному репозиторії відсутні каталоги Java-коду й тестів; цей workflow створює тільки планові/design-файли в каталозі специфікації. Структура `docs/` вище — ціль, визначена специфікацією, а не вже реалізовані файли.
