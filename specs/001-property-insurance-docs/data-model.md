# Модель даних і концептуальних класів

Цей документ фіксує предметні сутності та їхні зв'язки для майбутніх діаграм і CRC-карток; він не є Java-кодом чи схемою бази даних. Постійне зберігання даних не передбачається. Текстові пояснення наведено українською, програмні назви — англійською.

## Класи-кандидати

Кожен клас на майбутній діаграмі повинен мати щонайменше один атрибут або метод і конструктор. Остаточний перелік має бути синхронізований із CRC-книгою: одному класу діаграми відповідає рівно одна картка.

| Назва класу | Призначення та основні дані | Конструктор | Операції / перевірки |
|---|---|---|---|
| `Customer` | Страхувальник; ідентифікатор і контактні дані. | `Customer(id, contactDetails)` | Створює заявку/страхову заяву; переглядає власні поліси. |
| `InsuranceAgent` | Агент, що опрацьовує заявку, договір, статус і виплату. | `InsuranceAgent(operationSimulator)` | Розраховує показовий тариф; оновлює допустимий статус; ініціює симуляцію виплати. |
| `PropertyExpert` | Експерт-оцінювач. | `PropertyExpert()` | Проводить оцінку майна або збитку через відповідну абстракцію. |
| `Property` | Об'єкт страхування; ідентифікатор, адреса/опис, заявлена вартість. | `Property(id, description, declaredValue)` | Перевіряє повноту й коректність даних до створення заявки. |
| `InsuranceApplication` | Заявка клієнта, пов'язана з `Customer`, `Property` та оцінкою; має стан. | `InsuranceApplication(customer, property)` | Подання та переходи до розгляду, оцінки, пропозиції або відмови. |
| `InsurancePolicy` | Договір/поліс із номером і статусом. | `InsurancePolicy(policyNumber, customer)` | Активація та лише допустиме оновлення статусу; завершений поліс не змінюється. |
| `Claim` | Страхова заява, пов'язана з активним полісом і оцінкою збитків. | `Claim(policy, description)` | Подання та перехід до оцінювання, рішення або виплати. |
| `Assessment` *(абстрактний)* | Спільна абстракція результату оцінки: ідентифікатор, сума, стан/дата. | `Assessment(id)` | Абстрактна операція оцінювання; не створюється без конкретного виду оцінки. |
| `PropertyAssessment` | Оцінка вартості `Property`. | `PropertyAssessment(property)` | Реалізує оцінювання вартості; результат передається агенту. |
| `DamageAssessment` | Оцінка збитку для `Claim`. | `DamageAssessment(claim)` | Фіксує додатну або нульову суму; нульовий збиток не породжує виплату. |
| `Payment` | Нарахування/стан виплати за `Claim` і `InsurancePolicy`. | `Payment(claim, policy, amount)` | Обчислює показову суму; майбутня Java-операція `calculateAmount()` позначається `final` відповідно до `FR-008`; фактична виплата не виконується. |
| `OperationSimulator` *(інтерфейс)* | Абстракція повідомлення про навчальну зовнішню операцію. | Не застосовується до інтерфейсу. | Визначає `simulatePayment(payment)`; інтерфейс не виконує реального платежу чи мережевої взаємодії. |
| `ConsoleOperationSimulator` | Консольна реалізація `OperationSimulator`. | `ConsoleOperationSimulator()` | Реалізує `simulatePayment(payment)`, виводячи повідомлення без звернення до сервісу чи БД. |

Якщо під час деталізації діаграми будь-який із цих кандидатів буде вилучений, потрібно одночасно звірити акторів/типи послідовності, зв'язки, `FR-007` та склад CRC-книги. Не додавати класи, що не мають окремої відповідальності.

## Зв'язки

| Зв'язок | Кратність / значення |
|---|---|
| `Customer` — `Property` | Один клієнт може мати кілька об'єктів; власність/агрегація, якщо життєвий цикл об'єкта не залежить від заявки. |
| `Customer` — `InsuranceApplication` | Клієнт подає заявки; кожна заявка має одного страхувальника. |
| `InsuranceApplication` — `Property` | Кожна заявка стосується майна; недійсні дані відхиляються до створення заявки. |
| `InsuranceApplication` — `PropertyAssessment` | Заявка використовує результат оцінки майна; діаграма показує відповідний зв'язок, а не лише тип параметра. |
| `InsuranceApplication` — `InsurancePolicy` | Прийнята заявка може породити один поліс; відхилена — ні. |
| `Customer` — `InsurancePolicy` | Клієнт переглядає лише власні поліси; це не надає йому права змінювати статус. |
| `InsurancePolicy` — `Claim` | Страхова заява належить полісу; подання дозволене лише для активного поліса. |
| `Claim` — `DamageAssessment` | Для заяви фіксується оцінка збитків; нульова сума є явним результатом. |
| `Claim` — `Payment` | Виплата створюється лише для схваленого випадку з належним результатом оцінки. |
| `OperationSimulator` — `Payment` | Операція `simulatePayment(payment)` приймає `Payment`; на діаграмі це посилання має бути показано залежністю. |
| `Assessment` ← `PropertyAssessment`, `DamageAssessment` | Наслідування конкретних видів оцінки від абстрактної сутності. |
| `PropertyExpert` — `PropertyAssessment`, `DamageAssessment` | Експерт створює/передає відповідний результат оцінювання. |
| `InsuranceAgent` — `InsuranceApplication`, `InsurancePolicy`, `Payment` | Агент виконує відповідні бізнес-операції та оновлює лише допустимі стани. |
| `InsuranceAgent` — `OperationSimulator` | Залежність від інтерфейсу; реалізацію передають через конструктор або setter. |
| `ConsoleOperationSimulator` — `OperationSimulator` | Реалізація інтерфейсу консольним повідомленням. |
| `Payment` — `InsurancePolicy` | Нарахування пов'язане з договором, але не означає виконання реального платежу. |

Кожне поле або параметр, що посилається на інший клас (наприклад, `property: Property` чи `policy: InsurancePolicy`), має відповідати одному з показаних зв'язків на діаграмі класів (`FR-010`).

## Стан і правила переходів

Наведені стани — проєктне покриття вимог, а не нові тарифи чи правові правила. Точні enum-назви, якщо потрібні на діаграмі, є програмними ідентифікаторами англійською; написи станів у діаграмі — українською.

| Об'єкт | Запланований життєвий цикл | Обмеження |
|---|---|---|
| `InsuranceApplication` | чернетка → подана → на розгляді → оцінена → тариф розраховано → прийнята / відхилена | Неповне або недійсне майно не створює подану заявку. |
| `InsurancePolicy` | очікує активації → активний → завершений / скасований | Після завершення немає допустимого оновлення; перевірка статусу виконується до зміни. |
| `Claim` | подана → оцінюється → схвалена / відхилена → виплату нараховано | Нульова оцінка веде до явного рішення без нарахування виплати; неактивний поліс не приймає заяву. |
| `Payment` | не нараховано → нараховано → симуляцію зафіксовано | Усі зовнішні кроки — лише повідомлення у консолі. |

## Контроль узгодженості

- Три ролі зі специфікації мають відповідні програмні типи для учасників взаємодії.
- Об'єкти послідовності використовують лише типи, присутні на діаграмі класів.
- Кожна згадка класу у полі/параметрі відповідає діаграмному зв'язку.
- У CRC-книзі є картка для кожного класу, що фактично залишиться на діаграмі; заголовки карток точно збігаються з іменами класів.
- Кожна картка має дві колонки — «обов'язки класу» і «з ким співпрацює»; не більш як чотири короткі відповідальності формату «дієслово + іменник».
- Слова `interface`, `abstract` і `final` описують програмні властивості, тоді як український текст діаграм лишається пояснювальним.
